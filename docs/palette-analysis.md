# 配色提案ロジックの分析（2026-11-05）

対象: `src/palette-engine.js`（v0.1.0）。10語彙セット × seed 3種 × 24案 = **720案** を生成して採点した。採点スクリプトは作業用（未コミット）。

## 1. 結果

**47%（335/720）に何らかの問題があった。**

| 問題 | 件数 | 割合 | 判定基準 |
|---|---|---|---|
| メインが背景に弱い | 170 | 24% | メインと背景のコントラスト 3:1 未満 |
| 差し色が背景に埋もれる | 131 | 18% | 差し色と背景 1.6:1 未満 |
| メインとサブが近すぎる | 77 | 11% | ΔE 12 未満 |
| 濁った中間色が2色以上 | 53 | 7% | 彩度 0.03〜0.075・明度 0.42〜0.72 が2役割以上 |
| サブが背景に近い | 47 | 7% | 明度差 0.08 未満 |
| 差し色が一番鮮やかでない | 23 | 3% | — |

- 語彙別（問題数/72案）: かわいい 63・明るい 55・元気 38・落ち着いた 37・ナチュラル 34 … 誠実 16・明るい＋知的 14。**明るい系の語ほど悪い。**
- 調和別（問題数/案数）: 単色階調 77/146・補色 62/92・類似色 69/102・トライアド 58/101・分裂補色 57/106・**差し色 12/173**（無彩色＋差し色はほぼ問題なし）。
- 基準は私が置いた目安で、評価セットによる検証前。ただし悪い例は目で見ても明らか（下）。

悪い例（背景 / メイン / サブ / 差し色）:

- 明るい・暖色 × 鮮やか × 分裂補色: `#EDEFE1` / `#929E00`（オリーブ）/ `#AEF3A9` / `#DF59E1`
- 明るい・寒色 × 鮮やか × トライアド: `#F2F7FC` / `#0E94FA` / `#F0899A` / `#78B600`
- かわいい・寒色 × 鮮やか × トライアド: `#E8FAFE` / `#00AFC8` / `#FFC5F5` / `#CEA800`

比較: 画面案で手で選んだ7案は、メインと背景のコントラストが 3.2〜10.4:1。背景の明度は 0.96〜0.99・彩度 0.016 以下。サブは明度 0.75〜0.88 の淡い色、差し色は 3色の中でほぼ一番鮮やか。

## 2. 原因（コード上）

1. **役割ごとの明度の設計がない。** メインの明度は語彙の `pL` の範囲から乱数で取り、背景との明度差が 0.25 未満のときだけ補正している（`generatePalette` 末尾）。OKLCH の明度差 0.25 はコントラスト約 2:1 なので、「明るい」「かわいい」では淡い地に淡いメインが残る。
2. **差し色の明度が背景と無関係に 0.66〜0.84 固定。** 淡い地（明度 0.95 以上）では、目立つかどうかが彩度だけで決まる。
3. **サブはメインの明度＋0.08〜0.18・彩度 0.6〜0.75 倍。** 「メインの少し明るい版」になりやすく、メインに近すぎるか背景に近すぎる。実際の配色では、サブは「淡い面（帯・囲み）」か「メインより暗い締め色」のどちらかで、役割が決まっている。
4. **色相を回すだけの調和。** トライアドや補色で、同じくらいの彩度の色を3つ並べている。色相ごとの出せる彩度の上限（黄は明るい側、青は暗い側でしか鮮やかにならない）を見ていないため、ぎらついた色（`#0E94FA`）や濁ったオリーブ（`#929E00`）が出る。
5. **選ぶ基準が「離れていること」と「印象に合うこと」だけ。** 最遠点選抜は「既存案から一番遠い案」を選ぶので、極端な案ほど選ばれやすい。品質（読みやすさ・まとまり）の点数がない。

## 3. 改善方針（案）

画面案で手で選んだときの考え方（Claude Design で配色を決めるときの手順）をエンジンに移す。

1. **役割ごとの明度の段取りを先に決める。** 色相より先に、役割の型を選ぶ。
   - 淡い地: 背景 明度 0.96〜0.99・彩度 0.02 以下 → メインは背景と 4.5:1 以上（見出しにも使える濃さ）→ サブは明度 0.78〜0.9 の淡い面か、メインより暗い締め色 → 差し色は背景と 2.5:1 以上。
   - 濃い地（反転）: 背景 明度 0.15〜0.25 → メインは明るく、差し色は明るく鮮やか。
   - 無彩色＋1色: 今の「差し色」型（問題が少ない）をこの型の手本にする。
2. **彩度に順位を付ける。** 原則は「差し色 ≧ メイン > サブ > 背景」。高彩度（0.16 以上）は多くて2色まで。
3. **色相ごとの彩度の上限を使う。** その明度・色相で sRGB に入る最大彩度を求め、その何割かで指定する（例: 鮮やか 0.85、中間 0.6、くすみ 0.35）。黄緑〜オリーブの濁りは、明度と色相の組み合わせで避ける。
4. **調和は差し色に効かせる。** メインとサブは同系色（±30°）か無彩色にし、補色・分裂補色・トライアドの関係は差し色にだけ使う。3色すべてを色相環に散らさない。
5. **品質の点数で足切りしてから、多様性で選ぶ。** 上の §1 の判定を関数にして（`src/` の純粋関数）、合格した案の中から最遠点選抜する。
6. **テスト**: 既存のテスト（seed 再現・ロック不変・AA・多様性・印刷時の彩度）は、具体的な HEX を固定していないので維持できる見込み。品質の判定（メイン 3:1 以上、差し色 2:1 以上など）を全案に課すテストを足す。`tests/` の変更になるので、内容は先に提示する。

## 4. 確認したいこと

- 型（淡い地・濃い地・無彩色＋1色）の比率。案: 淡い地 6・無彩色＋1色 2・濃い地 1。
- 「かわいい」「元気」のような明るい語でも、メインは見出しに使える濃さ（4.5:1）まで下げてよいか。淡いメインを残すなら、その型には「見出しは文字色で」という注記を付ける。

## 5. 実施結果（2026-11-05、同日）

§3 の方針で `src/palette-engine.js` を作り直した（API・seed 再現・ロック不変は維持）。

- 生成の手順を「背景（淡い地）→ メイン（背景と 3.3:1 以上）→ サブ（淡い面か暗い締め色）→ 差し色（調和は差し色だけ、背景と 2.3:1 以上）→ 文字」に変更。
- 色相ごとの彩度の上限（`maxChroma`）で彩度を決め、黄〜黄緑（80〜125°）はメインにせず淡い面へ回す（濃くするとオリーブに濁るため）。
- 品質の判定 `qualityIssues()`（§1 の基準）を純粋関数として追加し、幅広く探す・深掘りの候補はこれに合格したものだけから選ぶ。
- 印象適合度は、読みやすさの補正をする前の主役色で評価する（補正は可読性のためで、印象の向きは変えない）。
- `color-utils.js` の `ensureContrast` を二分探索に変更（結果は従来の 0.01 刻みの最小段と同じ）。

| 指標 | 変更前 | 変更後 |
|---|---|---|
| 問題のある案（§1 の基準・720案） | 47% | 5% |
| メインが背景に弱い | 24% | 0% |
| 差し色が背景に埋もれる | 18% | 0% |
| 残る主な指摘 | — | サブが背景に近い 3%（判定基準より生成側の閾値が緩い分）、差し色が一番鮮やかでない 2% |
| 24案の生成時間（Node） | 約0.3〜0.5秒 | 約0.5秒 |

`npm test` 44件（品質テストを追加）・E2E 28件合格。

### 追加したテスト（tests/engine.test.js）

```js
test('品質: 全案がメイン3.2:1・差し色2.2:1以上で、qualityIssues に合格する', () => {
  for (const moods of [['明るい'], ['かわいい'], ['高級感'], ['明るい', '知的']]) {
    for (const p of generateWide({ index, moods, seed: 1 })) {
      assert.deepEqual(qualityIssues(p.colors), [], `${moods} ${JSON.stringify(p.colors)}`);
    }
  }
});
```
